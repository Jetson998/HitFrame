# HitFrame 已知限制与故障处理（种子客户交付）

给种子客户运维/支持人员用���排障参考。每条限制都注明了产品侧的应对措施；每个故障场景给出诊断命令和处理方式。

## 一、已知限制

### 1. 引擎输出尺寸为弱约束（非精确像素）

**现象**（2026-07-19 实测）：请求 `1024x1024` 实际返回 `1086×1448`（约 3:4）；请求 `1536x1024` 实际返回 `1402×1122`（约 5:4）。图像引擎只大致遵循「方向」（横/竖/方），不保证精确像素。

**产品侧应对**：
- 系统记录**实际返回尺寸**到资产的 `meta` 字段，前端按实际尺寸展示，不假装是请求尺寸
- 「比例」选项的文案是方向性描述，不承诺精确像素
- 如客户业务对精确尺寸有硬性要求（如平台上传规��），需要在下载/使用前自行按目标比例裁切；本系统当前不做自动裁切

**排查**：如怀疑某张图尺寸异常，查该 Job 对应资产的 `meta.actualSize`（或类似字段），与请求的 `ratio` 参数对比即可确认是否属于此已知现象。

### 2. 单租户架构（一次部署 = 一个客户）

系统按单租户交付：一份部署对应一个 `API_TOKEN`、一个数据库、一份点数余额。**不支持在同一部署里给多个客户分别开户**。如需服务多个客户，需要各自独立部署（各自 `.env`）。

### 3. 内容审核由供应商侧决定

生成请求可能因供应商内容审核被拒（`JOB_ENGINE_REJECTED`，见下方错误码表）。审核标准由引擎供应商（muskapis/gpt-image-2）掌握，本系统不做二次审核也无法预判是否会被拒。

### 4. 点击焦点环在鼠标点击时也会显示（P2，视觉细节）

设计预期是仅键盘 Tab 导航时显示蓝紫焦点环，当前实现在鼠标点击后也会短暂显示。不影响功能，属于后续视觉微调项。

## 二、失败与退款机制（重要：客户支持人员必读）

**核心规则：所有失败的生成任务都会自动退还点数，客户不会因为生成失败而被扣点。**

失败分两类：

| 类型 | 行为 |
|---|---|
| **可重试**（`retryable`，如引擎超时/繁忙） | 系统自动重试，最多 3 次；3 次仍失败才判定终态失败并退款 |
| **不可重试**（`non_retryable` / `moderation_rejected`，如内容被拒/输入无效） | 立即判定终态失败并退款，不重试 |

**客户端可见错误码与对应文案**：

| 错误码 | 类型 | 用户看到的文案 |
|---|---|---|
| `JOB_ENGINE_TIMEOUT` | 可重试 | 引擎响应超时，已自动重试 |
| `JOB_ENGINE_BUSY` | 可重试 | 引擎繁忙，已自动重试 |
| `JOB_ENGINE_REJECTED` | 内容审核拒绝 | 内容未通过引擎审核 |
| `JOB_ENGINE_ERROR` | 不可重试 | 引擎返回错误 |
| `JOB_INPUT_INVALID` | 不可重试 | 输入素材缺失或已删除 |
| `JOB_RESULT_INVALID` | 可重试 | 结果图片校验失败，已自动重试 |
| `JOB_STORAGE_ERROR` | 可重试 | 结果保存失败，已自动重试 |
| `JOB_INTERRUPTED` | 可重试 | 执行中断，已恢复或待恢复（服务重启导致，见下方场景） |

对外文案统一脱敏，不会包含内部路径、堆栈或密钥。原始错误信息只进服务端日志。

**如果客户反馈「点数被扣了但没出图」**：先查该次生成对应租户的点数流水（见下方核对命令），99% 是流水已经走了 `hold → refund` 但前端展示滞后或客户没刷新余额；如果流水显示 `hold` 之后没有对应的 `refund`/`settle`，才是真正的账本问题，需要联系开发排查。

## 三、故障处理场景

### 场景 1：怀疑点数账本不一致

**诊断**：
```bash
docker exec <postgres容器名> psql -U hitframe -d hitframe -c \
  "SELECT (SELECT points_balance FROM tenants WHERE id='<租户ID>') AS balance,
          (SELECT sum(amount) FROM credit_transactions WHERE tenant_id='<租户ID>') AS ledger_sum;"
```
两个数字应该**完全相等**。不相等才是真实问题。

**处理**：系统内置对账机制（`CreditsService.reconcile`），发现不一致会自动以流水重新计算余额并告警日志。如需人工确认某个客户的账本，把上面两个数字发给开发排查，不要直接手改 `tenants.points_balance`。

### 场景 2：生成任务卡住不动（一直显示"生成中"）

**诊断**：
```bash
# 查是否有任务超过 10 分钟仍是 running
docker exec <postgres容器名> psql -U hitframe -d hitframe -c \
  "SELECT id, status, created_at FROM generation_jobs WHERE status='running' AND created_at < now() - interval '10 minutes';"
```

**处理**：
- Worker 进程是否还在运行（`ps aux | grep worker-main`）
- 如 Worker 曾重启，重启时会自动把中断任务标记失败+退款（`JOB_INTERRUPTED`），客户端会看到失败状态而不是永远转圈；如果查到的 running 任务确实卡住超过合理时长且 Worker 明显没在处理，重启 Worker 进程即可触发恢复

### 场景 3：查看失败任务清单（不改账，仅诊断）

```bash
node --env-file=.env scripts/ops/dead-letters.mjs --limit 50
```
列出 BullMQ 死信队列 + 数据库里状态为 `failed` 的任务（含脱敏错误码）。**该脚本只读，不会重放/改账**——失败任务已经退款，客户如需重试应在前端重新发起，不是靠后台重放（重放会导致重复出图但只扣一次点数，产品口径上明确不做）。

### 场景 4：API 无法访问 / 前端连不上

**诊断**：
```bash
lsof -i :3001 -i :5173   # 确认端口被 HitFrame 自己的进程占用，不是别的服务
curl http://localhost:3001/api/v1/health
```

**处理**：确认 API 进程存活、`.env` 里 `DATABASE_URL`/`REDIS_HOST` 指向的服务是否健康（`docker compose ps`）。

### 场景 5：图片打不开 / 显示损坏

- 检查 `STORAGE_DRIVER` 与实际存储是否匹配（比如配置是 `s3` 但对象存储服务没启动）
- `s3` 模式下签名 URL 有效期 `SIGNED_URL_TTL`（默认 900 秒），过期会自动刷新，正常访问不应遇到；如遇到，检查系统时间是否准确（签名校验对时钟偏移敏感）
